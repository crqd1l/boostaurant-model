# Boostaurant

ИИ-ассистент официанта: по номеру столика Telegram-бот отдаёт профиль гостя и топ-5
персональных рекомендаций по меню. Стек: PostgreSQL + Surprise SVD / scikit-learn
k-means + FastAPI + aiogram 3.x, всё в docker compose.

Проект ведётся по гранту Фонда содействия инновациям (заявка СтС-506790, договор
1105ГССС27/106900 от 17.10.2025). Целевой заказчик — ресторан с полным обслуживанием
в городе-миллионнике, на iiko, с базой от 500 гостей / 1000 заказов в месяц.

**Данные синтетические.** Реальной интеграции с iiko нет: гости и заказы генерируются
по 5 поведенческим архетипам (`data_gen/archetypes.py`), связь «столик → гость» — заглушка
(`api/iiko_stub.py`). Схема БД при этом намеренно повторяет формат iiko, чтобы промышленная
выгрузка легла в неё без преобразования.

## Репозиторий — ещё и доказательная база отчёта (жёсткое правило)

`otchet/1.1…1.5_*.md` — исходники отчёта по этапу гранта; `otchet/build.py` собирает из них
`Отчет_заполненный.docx` по шаблону. Числа в отчёте (97,1 % точности SVD, 84,4 % холодного
старта, 5393 взаимодействия, 300 гостей, 56 блюд, 19 молочных позиций) — это фактические
результаты кода, а не иллюстрация.

Поэтому:

- Изменение `ml/`, `data_gen/` или `db/schema.sql` может обесценить цифры в `otchet/`.
  Заметив такое — **сказать об этом явно** и назвать затронутые разделы.
- `.docx` правится только пересборкой через `otchet/build.py`; руками — никогда.
- Не выдумывать и не «подтягивать» метрики в `otchet/*.md`. Любое число там должно быть
  получено прогоном кода; если прогона не было — так и сказать.

## Три слоя рекомендаций

`ml/recommend.py` склеивает их по убыванию персонализации: **SVD** (гость есть в обученной
матрице) → **k-means cold-start** (есть хоть один заказ) → **popularity**. Слой возвращается
клиенту в поле `source` — официант должен видеть, насколько система знает гостя.

Гость попадает в матрицу SVD только при переобучении (`POST /retrain`), сколько бы заказов
ни сделал до этого.

## Неочевидные инварианты — ломать нельзя

Все четыре решения приняты по результатам измерений, разбор — в `otchet/1.5_платформа.md`:

1. **Оценка для SVD — доля блюда в заказах гостя (1..5), а не счётчик заказов.** Счётчик
   смешивает «любит блюдо» и «часто ходит»; модель начинает предсказывать популярность.
2. **`biased=False` у SVD.** Смещение блюда — это его популярность, и её вклад превышал
   вклад факторов вкуса. Популярность вынесена в отдельный слой, где ей место.
3. **Признаки k-means — средний чек + доли 12 категорий, без recency/frequency.** Доли,
   а не абсолютные величины: иначе кластеризация идёт по активности, а не по вкусу. RFM-признаки
   для новичка вырождены и стягивают всех в кластер «Гурман».
4. **Hard-фильтр по аллергенам применяется ко всему ранжированному списку, а не к топ-5,**
   и сопровождается бустом по доле категории в заказах гостя. Иначе гость с аллергией
   выпадает в «хвост» выдачи, где персонализации уже нет (сладкоежке предлагалось пиво).

Быстрые теги заметок в боте (`bot/keyboards.py`) обязаны совпадать со значениями
`menu_items.tags` — на этом держится связь «официант отметил аллергию → следующая же
рекомендация её учитывает».

## Данные

UUID в первичных ключах — потому что ими оперирует iiko. `TEXT[]` для `menu_items.tags`
и `customer_preferences.allergens` — фильтр по аллергенам сводится к пересечению массивов.
`customers.archetype` служебное, заполняется только генератором; в промышленных данных пусто.
Центральная таблица для ML — `order_items`.

Состав ПДн намеренно минимален (152-ФЗ): нет имени, пола, e-mail, бонусных балансов, карт
лояльности. Не добавлять поля «на будущее» — каждое требует обоснования в отчёте.
