# План реализации прототипа рекомендательной системы

> Цель: рабочий прототип, который по `customer_id` (или номеру столика через заглушку) выдаёт топ-5 блюд. Реальной интеграции с iiko нет — данные генерируем. Telegram-бот делаем **потом**; сейчас только БД + ML + API.

Связанные документы: [data_model_plan.md](data_model_plan.md) (поля iiko), [architecture.md](architecture.md) (алгоритмы, потоки).

---

## Что важно понять до начала (снимает кашу)

**SVD и k-means едят разные данные — не путать.**

| Модель | Что на входе | Откуда | Зачем |
|--------|--------------|--------|-------|
| **SVD** | тройки `(customer_id, menu_item_id, count)` | `order_items` | основные рекомендации для клиентов с историей |
| **k-means** | фичи клиента (RFM + доли категорий) | агрегаты из `orders`/`order_items` | cold-start: новый клиент → его кластер → популярное в кластере |
| **Popularity** | суммы заказов за 30 дней | `order_items` | крайний fallback: истории нет вообще |

**Ключевой вывод:** 90% ценности — история заказов (`order_items`), а НЕ профиль клиента (пол/возраст/лояльность). Профиль нужен только для k-means cold-start.

**Решения (зафиксированы):**
- rating для SVD = **count, нормированный внутри клиента** (доля блюда в его заказах, шкала 1..5). Изначально планировался простой count — на нём SVD выучил популярность вместо вкуса (см. этап 3).
- SVD обучается с **`biased=False`**. Это не тюнинг, а суть: item bias = популярность блюда, и она забивала персонализацию.
- данные генерируем **по архетипам клиентов** (не случайно!), иначе SVD нечему учиться.

## Этапы (по порядку)

### Этап 1 — SQL-схема (`db/schema.sql`)

5 таблиц. Минимум, достаточный для SVD + k-means + fallback:

- **`menu_items`** — `id, name, category, price, tags[], is_active`. Справочник блюд.
- **`customers`** — `id (uuid), phone, gender, birthday, loyalty_tier, first_order_date, registered_at, archetype`. Профиль. `archetype` — служебное поле, чтобы потом проверить, совпал ли кластер k-means с зашитым архетипом (валидация).
- **`orders`** — `id, customer_id (FK), created_at, total_sum, table_number`. Заголовок заказа.
- **`order_items`** — `id, order_id (FK), menu_item_id (FK), quantity, price`. Позиции. **Центральная таблица для ML.**
- **`customer_preferences`** — `customer_id (FK), allergens[], dislikes[]`. Для hard-фильтра (слой 2). Опционально в v1.

Проверка этапа: схема применяется в чистую БД без ошибок.

### Этап 2 — Архетипы и генератор (`data_gen/`)

**Архетипы (5 шт.)** — каждый задаёт вероятности заказа блюд по категориям:

| Архетип | Любит категории | Средний чек | Частота визитов |
|---------|-----------------|-------------|-----------------|
| Мясоед | стейки, бургеры, пиво | высокий | средняя |
| Вегетарианец | салаты, боулы, супы | средний | высокая |
| Сладкоежка | десерты, кофе, выпечка | низкий | высокая |
| Бизнес-ланч | супы, комбо, горячее | средний | очень высокая (будни) |
| Гурман | всё дорогое, вино | очень высокий | низкая |

**Генератор** делает:
1. Сначала меню (`menu_items`) — ~40-60 блюд по категориям, с ценами и тегами.
2. Клиентов (`customers`) — ~200-500, каждому случайно назначается архетип.
3. Для каждого клиента — N визитов (`orders`), в каждом визите блюда сэмплируются **из распределения его архетипа** (+ немного шума, чтобы не было идеально). Пишем `order_items`.

Проверка этапа: в БД есть данные; SQL-запрос «топ блюд по архетипу» показывает ожидаемый перекос (мясоеды берут стейки чаще).

### Этап 3 — SVD (`ml/train_svd.py` + часть `recommend.py`)

Обучение (библиотека Surprise):
```python
df = SELECT customer_id, menu_item_id, SUM(quantity) as cnt FROM order_items ... GROUP BY
# rating = доля блюда в заказах ЭТОГО клиента, растянутая на 1..5
df['rating'] = 1 + 4 * df.cnt / df.groupby('customer_id').cnt.transform('max')
data = Dataset.load_from_df(df[['customer_id','menu_item_id','rating']], Reader((1, 5)))
model = SVD(n_factors=100, n_epochs=250, biased=False)   # biased=False — критично
model.fit(data.build_full_trainset())
pickle.dump(model, 'ml/models/svd.pkl')
```

Инференс — `recommend_svd(customer_id, n=5)`:
```python
scores = [(iid, model.predict(customer_id, iid).est) for iid in active_menu_items]
return sorted(scores, key=..., reverse=True)[:n]
```

**Две ловушки, на которые напоролись (обе про одно — популярность вместо вкуса):**

1. **Сырой count** мешает «как сильно любит блюдо» и «как часто вообще ходит». Бизнес-ланч ходит 26 раз при меню из 4 комбо → его счётчики вдвое выше всех; гурман ходит 5 раз → всё низкое. Лечится нормировкой внутри клиента.
2. **`biased=True` (дефолт)** — модель предсказывает `global_mean + bias_клиента + bias_блюда + факторы`. Bias блюда — это популярность, одна на всех. Замер: `std(item_bias)=0.29` против `std(факторов)=0.22` — популярность весила больше личного вкуса, и «Бизнес-ланч №1» лез в топ-5 даже гурману.

Popularity не выбрасываем — она уместна, но отдельным слоем fallback (этап 5), для гостей без истории.

Проверка этапа (**самая важная**): взять клиента-мясоеда → в топ-5 должны быть мясные блюда, а не десерты. Если рекомендации мусорные → проблема в данных (этап 2), а не в модели.

Метрика: доля позиций топ-5, попавших в «свои» категории архетипа. **Результат: 83%** (цель гранта — >80%).

| Архетип | Попадание |
|---|---|
| sweet_tooth | 96% |
| business_lunch | 96% |
| meat_lover | 82% |
| vegetarian | 82% |
| gourmet | 58% |

Гурман отстаёт закономерно: 3–8 визитов (меньше всех данных) и самое размазанное распределение — 6 категорий против 5 у остальных.

### Этап 4 — k-means cold-start (`ml/train_kmeans.py`, `ml/features.py`)

1. Фичи клиента (`ml/features.py`): **средний чек + доли 12 категорий** = 13 чисел.
2. `StandardScaler` → `KMeans(n_clusters=5)`. Сохранить **одним артефактом**: скейлер + модель + топы кластеров (порознь бесполезны — номера кластеров после переобучения меняются).
3. Для каждого кластера заранее посчитать «топ блюд кластера».
4. `recommend_coldstart(customer_id)` → predict кластер → топ блюд кластера.

**RFM урезали до одной буквы — M.** Планировался полный RFM, но recency и frequency у новичка вырождены: `frequency` всегда 1, `recency` — дата единственного визита. Это не сигнал, а вредный шум: `frequency=1` делает любого новичка похожим на гурмана (единственный редкий архетип, 3–8 визитов), и кластер гурмана работал магнитом — в него утекали бизнес-ланчи, мясоеды, вегетарианцы.

Попадание новичка в свой кластер:

| Набор фич | 1 визит | 2 визита | 3 визита |
|---|---|---|---|
| RFM + категории | 69.7% | 75.3% | 78.3% |
| **чек + категории** | **79.0%** | **90.3%** | **95.3%** |

`monetary` остаётся: сумма единственного чека осмысленна (гурман 5800 vs сладкоежка 920), в отличие от «частоты = 1».

**Проверка этапа — двойная, и первая обманывает.** На полной истории ARI=1.000, purity=100% — идеальная диагональ «кластер × архетип». Но это меряет не тот режим: k-means видел 10–34 визита, а cold-start по определению получает новичка с одним заказом.

Честная проверка (новый клиент, один заказ, модель его не видела) — **79%**:

| Архетип | Попадание |
|---|---|
| sweet_tooth | 95% |
| gourmet | 82% |
| vegetarian | 78% |
| meat_lover | 76% |
| business_lunch | 65% |

### Этап 5 — единая функция рекомендации (`ml/recommend.py`)

```
recommend(customer_id):
    если клиент ЕСТЬ В ОБУЧЕННОЙ МАТРИЦЕ SVD → SVD (этап 3)
    иначе если есть хоть один заказ          → k-means cold-start (этап 4)
    иначе                                    → popularity fallback (топ-5 за 30 дней, SQL)
    → hard-фильтр по аллергенам/dislikes (слой 2)
    → добивка популярным, если фильтр срезал слишком много
    → top-5
```

**Условие для SVD — «клиент в матрице», а не «у клиента есть заказы».** Планировалось второе, но это ошибка: клиент попадает в матрицу только при переобучении, поэтому вчерашний гость с десятью визитами для SVD ещё не существует. Surprise на незнакомый ID молча возвращает **одну и ту же константу** (у нас 2.596) на все 56 блюд — сортировка такого списка даёт произвольный порядок, то есть мусор под видом персонализации.

Замер на клиентах, которых модели не видели:

| Визитов у новичка | SVD | cold-start |
|---|---|---|
| 1 | 40% | 82% |
| 3 | 40% | 92% |
| 10 | 25% | 100% |

40% у SVD — шум сортировки константы. Поэтому новичка **всегда** забирает cold-start, сколько бы заказов он ни сделал: до переобучения SVD ему нечего сказать. Это же объясняет, зачем в API нужен `POST /retrain`.

**Hard-фильтр — именно hard, а не понижение веса**: аллергия это безопасность, блюдо не должно всплыть ни при каком score.

**Ловушка: фильтр выбрасывает нас в «хвост» ранжирования, где персонализации уже нет.** У сладкоежки с аллергией на dairy+gluten под запретом 26 блюд из 56 — весь её сладкий топ. Первая версия добивала выдачу глобальным popularity, и официант получал «к десерту предложите пиво и курицу терияки» — топ продаж мясоедов, к её вкусу отношения не имеющий.

Причина глубже, чем добивка. SVD уверенно ранжирует то, что гость **брал**, а на остальном меню оценки сползают к шуму (у нас 1.8–2.4), где мясо и вино случайно оказываются выше кофе. Эспрессо и сорбет — ровно то, что подошло бы гостье — стояли на 14-м и 20-м местах со score **ниже курицы терияки**, только потому что она их никогда не заказывала. Обычно это неважно (показываем топ-5, который модель знает твёрдо), но фильтр сдвигает нас именно в этот хвост.

Лечится двумя вещами:
1. Фильтровать **полное** ранжирование слоя, а не первые `n*4` позиции; popularity — только последний рубеж, когда безопасных блюд физически не хватило.
2. `_boost_by_taste()` — мягкая прибавка к score, пропорциональная доле категории в заказах гостя (тот же вектор, что кормит k-means). Твёрдый топ не сдвигается (там разрыв велик), а хвост переупорядочивается в сторону вкуса.

Побочный эффект — основная метрика выросла: **83% → 88%**, причём гурман сильнее всех (58% → 71%). Логично: буст компенсирует ровно те случаи, где SVD не уверен, а гурману данных не хватало больше всех.

Проверка этапа: все три ветки отдают `source` (`svd` / `coldstart` / `popularity`), аллергены не просачиваются, выдача всегда полная.

### Этап 6 — FastAPI (`api/main.py`, `api/iiko_stub.py`)

```
GET  /recommendations?customer_id=<uuid>   → {source, items: [...]}
GET  /recommendations?table=<n>            → заглушка iiko: table→customer_id, дальше как обычно
POST /retrain                              → переобучить модели (демо)
GET  /health                               → жив ли сервис, загружены ли модели
```

В ответе есть `source` (`svd` / `coldstart` / `popularity`) — не отладка: официанту важно отличать персональную рекомендацию от «просто популярного».

**Заглушка iiko** (`api/iiko_stub.py`) — самый свежий заказ за столиком, аналог `/order/by_table`. Отдаёт наружу ровно то же, что даст боевая интеграция — `customer_id`, поэтому при переходе на реальную iiko меняется только этот модуль; `main.py` и `recommend.py` не трогаются.

**`/retrain` — не «кнопка для демо», а единственный способ попасть в персонализацию.** Клиент входит в матрицу SVD только при переобучении: до него новый гость навсегда остаётся на `coldstart`, сколько бы раз ни пришёл. Три вещи, которые тут легко сделать неправильно:

- **`cache_clear()` обязателен.** Модели закэшированы через `@lru_cache`. Без сброса процесс продолжит отдавать старую модель из памяти, и эндпоинт **молча соврёт об успехе**: `.pkl` на диске новый, рекомендации те же.
- **`cwd=PROJECT_ROOT`** для subprocess — uvicorn могут запустить откуда угодно.
- **Валидация не должна ронять обучение.** У боевого клиента `archetype = NULL` (служебное поле генератора), и `adjusted_rand_score` на `None` падает. Retrain ломался бы на первом же реальном госте — при том, что модель к этому моменту уже сохранена. Валидация теперь считается только по размеченным и пропускается на боевых данных.

В проде `/retrain` — фоновая задача по расписанию (в гранте: еженедельно), в паре с синхронизатором: сначала Поток B тянет свежие заказы из iiko, потом обучение. Синхронный HTTP отвалится по таймауту уже на нескольких тысячах клиентов.

Проверка этапа: все три ветки отдают корректный `source`; `POST /retrain` реально переводит новичка `coldstart → svd` (это же и проверка `cache_clear`); краевые случаи — 404 на пустой столик, 400 на «оба параметра» и «ни одного».

## Порядок и зависимости

```
Этап 1 (схема)
   └→ Этап 2 (данные)          ← без данных ничего не обучить
        ├→ Этап 3 (SVD)        ← ядро, делаем первым из ML
        └→ Этап 4 (k-means)    ← можно после SVD
             └→ Этап 5 (recommend) ← склеивает SVD+kmeans+fallback
                  └→ Этап 6 (API)
```

Делаем строго по цепочке. После каждого этапа — его «проверка», не переходим дальше пока не зелёная.

## Что НЕ делаем в прототипе
- Реальные запросы в iiko (Поток B / синхронизатор) — только текст в отчёте.
- Telegram-бот — потом, поверх готового API.
- Взвешенный rating, инкрементальное переобучение, версионирование моделей — улучшения.
