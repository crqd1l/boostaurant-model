# 1.5 Создание цифровой платформы для персонализации обслуживания

На данном этапе обучены рекомендательные модели и собрана работающая платформа: база данных, сервис рекомендаций и обученные модели объединены с разработанным ранее интерфейсом официанта. Проверен сквозной сценарий обслуживания — по номеру столика официант получает профиль гостя и персональные рекомендации по меню.

## Обучение модели коллаборативной фильтрации

Модель обучается на матрице взаимодействий «гость — блюдо», построенной из истории заказов: 5393 взаимодействия по 300 гостям и 56 блюдам. Реализация — метод SVD библиотеки Surprise.

При обучении приняты два решения, определившие качество рекомендаций.

**Нормировка оценки внутри гостя.** Исходное количество заказов блюда как оценка предпочтения непригодно: оно смешивает две разные величины — насколько гость любит блюдо и как часто он вообще посещает ресторан. Гость с 26 визитами набирает по любимым позициям вдвое большие счётчики, чем гость с пятью визитами, и модель обучается предсказывать популярность блюда вместо личного вкуса. В результате наиболее заказываемая позиция меню попадала в рекомендации всем гостям подряд. Оценка заменена на долю блюда в заказах данного гостя, приведённую к шкале от 1 до 5: любимое блюдо получает максимальную оценку независимо от частоты посещений, и величина становится сравнимой между редкими и частыми гостями.

**Отказ от учёта смещений.** Стандартная модель представляет оценку суммой среднего значения, смещения гостя, смещения блюда и латентных факторов вкуса. Смещение блюда есть его популярность — одинаковая для всех гостей. Измерение показало, что вклад смещений превышал вклад факторов вкуса, то есть популярность вытесняла персонализацию. Смещения отключены, и модель объясняет оценку исключительно латентными факторами. Популярность при этом не утрачена — она вынесена в отдельный слой для гостей без истории, где и уместна.

Качество оценивалось по доле позиций в первой пятёрке, относящихся к категориям меню, характерным для архетипа гостя (раздел 1.2). Результат по 300 гостям — **97,1 %** при целевом значении не менее 80 %.

| Архетип гостя | Доля корректных рекомендаций |
|---------------|------------------------------|
| Бизнес-ланч | 99,1 % |
| Мясоед | 98,5 % |
| Вегетарианец | 98,2 % |
| Сладкоежка | 96,1 % |
| Гурман | 93,8 % |

Наиболее низкий результат у архетипа «Гурман» закономерен: этот тип гостей посещает ресторан реже остальных (3–8 визитов против 18–34 у бизнес-ланча), располагает наименьшим объёмом истории и имеет наиболее широкое распределение по категориям меню.

## Рекомендации для новых гостей

Для гостя, отсутствующего в обученной модели, применяется кластеризация. Признаковое описание гостя составляют средний чек и доли двенадцати категорий меню в его заказах — тринадцать величин. Доли, а не абсолютные количества, использованы намеренно: абсолютные значения сделали бы вектор частого гостя большим по всем осям, и алгоритм сгруппировал бы гостей по активности вместо вкуса.

Классические признаки давности и частоты посещений, предусмотренные RFM-анализом, из описания исключены. Для нового гостя они вырождены — частота всегда равна единице, давность есть дата единственного визита, — и вносят не сигнал, а искажение: единичная частота делает любого новичка похожим на редко посещающего «Гурмана», и соответствующий кластер притягивал гостей всех типов. Средний чек сохранён: сумма единственного заказа осмысленна и разделяет гостя с чеком 5800 рублей и гостя с чеком 920 рублей.

Проверка выполнена на гостях, отсутствующих в обучающей выборке. Доля корректных рекомендаций при единственном визите — **84,4 %**, при трёх визитах — **97,2 %**.

| Архетип гостя | Один визит |
|---------------|------------|
| Гурман | 93,3 % |
| Мясоед | 86,0 % |
| Сладкоежка | 84,7 % |
| Вегетарианец | 80,7 % |
| Бизнес-ланч | 77,3 % |

Существенно, что проверка проводилась именно в режиме холодного старта. Оценка на гостях с полной историей даёт полное совпадение кластеров с архетипами, но этот показатель не отражает реального применения: алгоритм предназначен для гостя с единственным заказом.

## Учёт ограничений гостя

Блюда, содержащие отмеченные аллергены или нежелательные ингредиенты, исключаются из выдачи независимо от оценки модели.

При реализации выявлена особенность, потребовавшая доработки. Модель уверенно ранжирует блюда, которые гость заказывал, а на остальном меню оценки сближаются, и порядок в этой части списка определяется случайными различиями. Обычно это несущественно — официанту показываются первые пять позиций. Но если ограничения гостя исключают весь верх списка (гость с аллергией на молочные продукты теряет 19 позиций меню из 56, включая все десерты), выдача формируется именно из этой части, где персонализации уже нет. В первоначальной версии недостающие позиции добирались из общего списка популярных блюд, и гостю, предпочитающему десерты и кофе, предлагались пиво и мясные блюда — лидеры продаж, не имеющие отношения к его вкусу.

Решение состоит из двух частей: фильтрация применяется ко всему ранжированному списку, а не к его началу, а к оценке добавляется поправка, пропорциональная доле категории в заказах гостя. Уверенно ранжированный верх списка при этом не смещается, а нижняя часть переупорядочивается в соответствии со вкусом. Побочным результатом стал рост общей точности рекомендаций с 94,7 % до 97,1 %, наибольший — у архетипа «Гурман» (с 86,6 % до 93,8 %), которому недоставало данных сильнее прочих.

## Подключение интерфейса официанта

Интерфейс официанта в формате бота Telegram разработан в рамках первого этапа гранта. На данном этапе он подключён к созданной платформе и наполнен содержанием: все три доступных официанту действия обслуживаются сервисом рекомендаций.

**Рекомендация** — пять блюд с указанием категории и цены. Вместе с перечнем передаётся характер рекомендации: персональная, основанная на схожих гостях либо просто популярная. Официант видит, насколько система осведомлена о госте, и общий список не выдаётся за персональное предложение.

**Информация о госте** — уровень лояльности, число визитов, средний чек, дата последнего посещения, любимые блюда и, что наиболее важно, аллергены.

**Заметка** — отметки об аллергенах и антипредпочтениях либо произвольный текст. Отметки не являются справочными: их значения совпадают с тегами блюд, поэтому внесённое ограничение учитывается уже в следующей рекомендации этому гостю.

## Проверка работы платформы

Платформа развёрнута в полном составе — база данных, сервис рекомендаций, обученные модели — и проверена по сквозному сценарию. Ниже приведены фактические результаты обращений.

**Гость с историей заказов** (столик 5): 12 визитов, средний чек 918 рублей, любимые блюда — раф, латте, тирамису. Выдача, слой «персональные рекомендации»: латте, раф, тирамису, чизкейк, эспрессо. Рекомендации соответствуют предпочтениям гостя.

**Гость с ограничением по составу**: отмечена аллергия на молочные продукты. Выдача, слой «персональные рекомендации»: эспрессо, американо, бизнес-ланч № 1, ланч-сет с супом, бизнес-ланч № 2. Ни одна из 19 позиций меню, содержащих молочные продукты, в выдачу не попала; из напитков предложены единственные два вида кофе, приготавливаемые без молока.

**Гость без истории заказов**: выдача, слой «популярные блюда»: капучино, борщ, латте, паста карбонара, бизнес-ланч № 1 — позиции с наибольшими продажами за 30 дней. Официанту отображается пометка о том, что гость системе незнаком.

Проверены все три слоя формирования рекомендаций, механизм переключения между ними и исключение блюд по ограничениям гостя. Сквозной сценарий «номер столика → определение гостя → профиль и рекомендации» работает в полном объёме.
